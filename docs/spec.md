# Rearview Product and Technical Specification

## 1. Purpose

Rearview is a story-first code review app. Its goal is to make code review simpler, faster, more focused, and more effective for changes authored by humans, AI agents, or both.

Most review tools present a change as a filesystem-ordered list of diffs. Rearview instead presents each change as a coherent review narrative: the conceptual path a reviewer should follow to understand what changed, why it changed, where the risks are, and what context belongs in the code versus only in the review.

Rearview should support tiny changes, large multi-system changes, local repositories, GitHub Pull Requests, GitLab Merge Requests, AI-generated work-in-progress changes, self-review, and collaborative review. The initial product is a locally running app. It should be designed so a hosted app or Chrome extension can be added later, but neither should be required or assumed. Rearview is intentionally not a merge tool: users may review, comment, approve, request changes, or export guidance from Rearview, but merges must happen in Git or the source platform such as GitHub or GitLab.

## 2. Product principles

1. **A codebase is a story.** Developers should be able to follow flows such as request -> validation -> storage -> domain behavior -> response -> user interface -> observability.
2. **A pull request is a smaller story inside that larger story.** Review order should be chosen for comprehension, not by file path.
3. **Good code should not make reviews boring.** Rearview should reduce reviewer fatigue by collapsing low-risk boilerplate, surfacing important decisions, and pacing long reviews.
4. **Review intent should be explicit.** Comments should encode whether they are issues, suggestions, questions, praise, nits, or blockers so authors can respond without guessing tone.
5. **AI should assist, not obscure.** AI can organize, summarize, answer questions, and review, but every generated structure or comment must be inspectable, editable, and attributable.
6. **The review story should be portable.** Rearview-specific structure should be persisted in readable metadata and mirrored into GitHub/GitLab where possible.
7. **Local-first is the product shape.** A developer should be able to run Rearview against a local checkout without a Rearview-hosted service. Future hosted or extension surfaces should reuse the same core model without becoming prerequisites.

## 3. Target users and review modes

### 3.1 Reviewing AI changes

Users iteratively inspect and refine changes generated by AI coding agents.

Key needs:

- View uncommitted, staged, committed, or branch-level AI changes as a story.
- Ask questions on a line, hunk, file, section, or whole review.
- Route questions back to the agent/session that produced the change when available.
- Ask the AI to make follow-up edits from a comment thread.
- See what context the AI used when answering.
- Preserve review decisions and follow-up prompts as part of the review audit trail.

### 3.2 Reviewing another developer's PR/MR

Users inspect a GitHub Pull Request or GitLab Merge Request through Rearview while comments and review state sync back to the source platform.

Key needs:

- Import PR/MR metadata, commits, changed files, existing threads, CI checks, and review status.
- Reorder files and hunks into a narrative structure.
- Leave line comments with explicit intent, severity, and optional suggested patches.
- Emit comments as platform-compatible Markdown while preserving structured metadata.
- Reply to existing GitHub/GitLab threads.
- Submit review summaries and approval/request-changes states where supported.

### 3.3 Self-review

Authors review their own work before requesting review, and optionally shape how reviewers will see it.

Key needs:

- Edit section order, section names, descriptions, and reviewer notes.
- Add comments that call out tradeoffs, risky areas, migration notes, or intentional decisions.
- Persist the story structure as readable branch metadata.
- Optionally rewrite branch commits so each commit maps to a review section.
- Sync self-review notes to GitHub/GitLab as PR/MR comments or body sections.
- Read and respond to external reviewer comments from the same interface.

## 4. Core product experience

### 4.1 Review workspace

The primary screen is a review workspace optimized for desktop but responsive on mobile.

Desktop layout:

- Left rail: review outline, filters, agent reviewers, search, unresolved threads.
- Main pane: story sections containing collapsed/expanded files and diffs.
- Right pane: selected thread, AI chat, file context, symbols, and review checklist.

Mobile layout:

- Single-column story outline by default.
- Tap into section -> file -> hunk -> thread.
- Persistent bottom actions for comment, ask AI, mark reviewed, and next item.
- Thread and AI chat appear as slide-over panels.

### 4.2 Story sections

A review is organized as one or more ordered sections. Each section has:

- Title.
- Purpose summary.
- Reviewer guidance: what to focus on and what can likely be skimmed.
- Risk level.
- Related files, hunks, commits, tests, and threads.
- Optional dependencies on earlier sections.

Example:

1. Add persistence model and migration.
2. Implement domain behavior and validation.
3. Expose API endpoint.
4. Add UI and copy updates.
5. Cover behavior with tests and observability.

### 4.3 Expansion levels

Each file in a section supports progressive disclosure:

1. **Collapsed:** file path, role in section, risk badges, thread count.
2. **Outline:** changed symbols, public interfaces, test names, generated-file detection, and important hunks.
3. **Diff:** full changed hunks with surrounding context.
4. **Full file:** entire current file with changed regions highlighted.
5. **Compare context:** optional links to callers, callees, related tests, and previous implementation.

### 4.4 Review pacing

Rearview should help reviewers maintain quality during long reviews:

- Mark section/file/hunk as reviewed.
- Show progress by risk and by story section, not just by file count.
- Offer reviewer breakpoints after major sections.
- Remember scroll position and collapsed state.
- Surface unresolved high-risk comments before approval.
- Detect when new commits invalidate already-reviewed sections.

### 4.5 Comment intents

Rearview stores comments as structured records and renders them to Markdown for external platforms.

Initial intent taxonomy:

- `issue`: Something should change before merge.
- `suggestion`: Optional improvement.
- `question`: Clarification needed.
- `nit`: Small non-blocking polish.
- `praise`: Positive feedback.
- `thought`: Context or observation.
- `blocking`: Must resolve before merge.
- `todo`: Follow-up work, either now or later.

Structured fields:

- Intent.
- Severity: info, low, medium, high, critical.
- Scope: line, hunk, file, section, review.
- Confidence: low, medium, high.
- Suggested patch, if any.
- Requires response: yes/no.
- Source: human, named agent, imported platform.

Markdown rendering example:

```markdown
**issue (medium, requires response):** This migration is not reversible.

Could we add a down migration or document why rollback is not supported?

<!-- rearview:comment {"intent":"issue","severity":"medium","requiresResponse":true} -->
```

## 5. AI capabilities

### 5.1 Story generation

For a review target, AI proposes an ordered story from available signals:

- Git diff and commit history.
- PR/MR title, description, linked issues, and comments.
- File paths, dependency graph, symbols, and tests.
- Existing Rearview metadata.
- Optional user-provided review goals.

The AI returns structured JSON containing sections, rationales, file/hunk assignments, risk levels, and reviewer guidance. The user can accept, edit, regenerate, or manually build the story.

### 5.2 Risk and attention guidance

AI should identify likely review hotspots, such as:

- Security-sensitive code.
- Data migrations and destructive changes.
- Public APIs and schema changes.
- Complex logic and branching.
- Missing or weak tests.
- Performance-sensitive paths.
- Error handling, observability, and rollback behavior.
- Generated or mechanical changes that can be skimmed.

AI guidance must be treated as advisory. Rearview should distinguish model inference from deterministic facts.

### 5.3 Contextual Q&A

Users can ask questions at any review scope. Rearview should include the smallest useful context window:

- Selected lines/hunk.
- Surrounding symbols.
- Section summary.
- Related files and tests.
- Prior comments in the thread.
- Agent session transcript when available and authorized.

Answers should cite the files, hunks, commits, comments, or session messages used.

### 5.4 AI reviewer agents

Rearview supports configurable AI reviewers that participate like human reviewers: starting threads, replying to threads, and writing review summaries.

Default agents:

#### Maintainer

Focuses on consistency with existing repo vocabulary and patterns, maintainability, edge cases, test coverage, and implementation simplicity.

#### Time traveler

Focuses on future debuggability, decision rationale, migration completeness, extensibility, and whether context is preserved in durable places.

#### On-call engineer

Focuses on observability, failure modes, performance, operational simplicity, alertability, and rollback or remediation paths.

Agent controls:

- Enable/disable per review.
- Configure custom instructions and forbidden areas.
- Limit to specific sections or files.
- Set comment budget and severity threshold.
- Run in draft mode before publishing comments.
- Require human approval before posting externally.

### 5.5 Linking to AI authoring sessions

Rearview should support optional session adapters for AI tools. The first implementation should use a generic session manifest:

```json
{
  "schema": "rearview.ai-session.v1",
  "tool": "example-agent",
  "sessionId": "abc123",
  "createdAt": "2026-06-11T00:00:00Z",
  "repository": "file:///repo",
  "branch": "feature/story-review",
  "baseRef": "main",
  "messagesPath": ".rearview/sessions/abc123/messages.jsonl",
  "commitShas": ["..."]
}
```

Adapters for specific tools can enrich this with native deep links, transcript retrieval, and follow-up edit commands.

## 6. Source and platform support

### 6.1 Repository sources

Initial source abstraction:

- Local filesystem path.
- Git remote over SSH/HTTPS cloned into a local cache.
- GitHub repository/PR through API.
- GitLab repository/MR through API.

All sources normalize into:

- Repository metadata.
- Base/head refs.
- Commits.
- Changed files.
- Hunks and line mappings.
- Platform comments and review states.
- CI/check statuses when available.

### 6.2 Provider capabilities

Provider adapters should declare capabilities instead of assuming feature parity:

- Can read pull/merge request metadata.
- Can post line comments.
- Can post review summaries.
- Can submit approve/request-changes states.
- Can read/write suggestions.
- Can resolve threads.
- Can edit PR/MR body.
- Supports draft comments.

### 6.3 Local-only mode

Local-only mode avoids any Rearview-hosted service and can run without network access after dependencies are installed, unless the user chooses to sync with GitHub/GitLab or call an AI provider.

Supported inputs:

- Working tree diff.
- Staged diff.
- Branch against base ref.
- Commit range.
- Patch file.

Outputs:

- Local Rearview metadata.
- Markdown review summary.
- Optional patch files for suggested fixes.
- Optional commit history rewrite commands.

## 7. Persistence and data model

### 7.1 Local project metadata

Rearview stores local state under `.rearview/` by default. This directory should be human-readable and safe to inspect.

Proposed files:

- `.rearview/review.json`: current review story, comments, source metadata, and preferences.
- `.rearview/sessions/*.json`: linked AI session manifests.
- `.rearview/cache/`: derived symbol indexes, provider responses, and AI outputs.

Projects can choose to commit selected metadata. Sensitive cache files and transcripts should be ignored unless explicitly opted in.

### 7.2 Review story schema

Minimal story schema:

```json
{
  "schema": "rearview.review.v1",
  "source": {
    "kind": "local",
    "baseRef": "main",
    "headRef": "feature/example"
  },
  "sections": [
    {
      "id": "persistence",
      "title": "Add persistence model and migration",
      "summary": "Introduces storage needed by later API changes.",
      "risk": "high",
      "reviewerFocus": ["migration rollback", "data compatibility"],
      "items": [
        {
          "kind": "file",
          "path": "db/migrations/001_add_widgets.sql",
          "hunks": ["@@ -0,0 +1,20 @@"]
        }
      ]
    }
  ],
  "comments": []
}
```

### 7.3 Git commit story metadata

When rewriting or preparing commits for Rearview, each commit should represent a coherent story section where practical. Commit messages should include a readable trailer:

```text
Rearview-Section: persistence
Rearview-Section-Title: Add persistence model and migration
Rearview-Review-Schema: rearview.review.v1
```

Rearview can detect these trailers and seed section order from commit history.

## 8. Architecture

### 8.1 Technical choices

Rearview should be built as a TypeScript web application with a shared core package and environment-specific adapters.

Recommended stack:

- **Language:** TypeScript for shared frontend, backend, and provider logic.
- **UI framework:** React with a routing framework that runs well as a locally served app and can later support extension or hosted surfaces if those become valuable.
- **Styling:** Tailwind CSS plus accessible component primitives.
- **Diff rendering:** A custom virtualized diff viewer over parsed git hunks so the app can support story sections, progressive expansion, line comments, and mobile rendering.
- **Git operations:** `isomorphic-git` where it fits, plus local Git/Node operations for filesystem access, SSH remotes, native Git behavior, and working-tree inspection.
- **Local app runtime:** Node.js CLI that serves the web app and exposes local repository operations over localhost.
- **Database/query layer:** SQLite for local metadata, with a typed query/migration layer such as Drizzle ORM so the schema can later move to another runtime if needed.
- **AI integration:** Provider-abstracted AI service with structured outputs for story generation and reviewer agents. The app should support multiple AI sources from the start, at minimum Codex and Claude, and must not hard-code one model provider.
- **Auth:** Environment variable tokens for the initial local app: GitHub and GitLab provider tokens, plus AI provider tokens for sources such as Codex and Claude. Later versions may add OAuth, OS keychain storage, browser extension auth, or hosted secrets, but the initial implementation should not require them.
  Initial configuration should document expected variables such as `GITHUB_TOKEN`, `GITLAB_TOKEN`, `OPENAI_API_KEY` or a Codex-specific token, and `ANTHROPIC_API_KEY` for Claude.
- **Background work:** A job abstraction that runs in-process locally first and can later be backed by another runtime if a hosted app or extension needs it.
- **Packaging:** Monorepo with shared packages for core model, providers, AI, UI, CLI, and app.

Why this stack fits:

- TypeScript maximizes reuse between the local web app, local server, possible future extension surfaces, and possible future hosted surfaces.
- A local Node runtime covers repository operations that browsers and extensions cannot safely perform directly.
- Shared provider abstractions keep GitHub, GitLab, local Git, and SSH workflows consistent.
- The same core data model can later power a Chrome extension or hosted app without making either part of the initial scope.

### 8.2 Package layout

Proposed repository structure once implementation begins:

```text
apps/
  web/                 # React app
  local-server/        # Node local runtime and API
packages/
  core/                # Review schemas, story model, comment model
  git/                 # Git diff parsing and repository adapters
  providers/           # GitHub/GitLab/local provider adapters
  ai/                  # AI orchestration, prompts, structured outputs
  ui/                  # Shared UI components
  diff-viewer/         # Virtualized diff and code outline components
  db/                  # Drizzle schema and migrations
skills/
  prepping-for-review/ # Agent skill for review-friendly commits
```

### 8.3 Backend boundaries

Core services:

- `ReviewSourceService`: normalizes local/git/provider inputs.
- `DiffService`: parses files, hunks, line mappings, and symbols.
- `StoryService`: creates, edits, validates, and persists review stories.
- `CommentService`: manages structured comments and Markdown rendering.
- `ProviderSyncService`: imports/exports PR/MR comments and review state.
- `AiStoryService`: proposes review stories and risk guidance.
- `AiReviewerService`: runs configurable reviewer agents.
- `SessionLinkService`: links AI authoring sessions and routes follow-up questions.

### 8.4 API style

Use a typed RPC-style API for app-internal calls, plus explicit provider adapter interfaces. The local server is the only initial API runtime. Keep handler boundaries portable so a future hosted app or extension bridge can reuse them if those surfaces are added.

Important endpoint families:

- Open/select repository.
- Create review target.
- Fetch normalized diff.
- Generate or update story.
- Update section order/metadata.
- Create/update/delete comment.
- Render/export comments.
- Sync with provider.
- Run AI reviewer.
- Ask AI about selection.

### 8.5 Security and privacy

Security requirements:

- Default to local-only processing for local repositories.
- Require explicit consent before sending code to AI providers.
- Show a preview of context that will be sent to AI.
- Redact configured secret patterns before AI calls.
- Read GitHub, GitLab, Codex, Claude, and other provider tokens from environment variables in the initial local app.
- Do not persist provider tokens in `.rearview/` or other project metadata.
- Leave room for later credential mechanisms such as OS keychain storage, OAuth, browser extension auth, or hosted secret storage.
- Treat AI session transcripts as sensitive.
- Support workspace-level ignore patterns for files that must never be sent to AI.

## 9. Non-goals for the first release

- Replacing GitHub/GitLab as the source of truth for pull request or merge request review state.
- Fully automatic code approval.
- Merging changes. Rearview may sync review state and approvals where providers support them, but it must not merge pull requests, merge requests, branches, or local changes.
- Perfect semantic understanding for every language.
- Real-time multi-user collaboration.
- Browser extension support in the initial release. The architecture should leave this possible later.
- A hosted Rearview app in the initial release. The architecture should leave this possible later, but the local app is the only committed runtime for now.
- Commit rewriting UI beyond a generated plan/command preview.
- Full support for every Git hosting provider.

## 10. MVP definition

The first useful version should be a locally running app and should not require Rearview-hosted infrastructure.

MVP user flow:

1. User runs Rearview locally in a repository.
2. User selects a base ref and head ref or current working tree.
3. Rearview parses the diff.
4. Rearview creates a deterministic story from commits and file heuristics.
5. User can view the story, reorder sections/files, expand diffs, and mark items reviewed.
6. User can add structured comments.
7. User can export a Markdown review summary.
8. If an AI key is configured, user can ask for AI story generation and risk guidance.

MVP success criteria:

- A reviewer can understand a medium-sized change faster than in raw `git diff`.
- A self-reviewer can shape review order and produce useful reviewer notes.
- No Rearview-hosted account is required.
- All review metadata is readable on disk.

## 11. Implementation plan

### Phase 0: Repository foundation

Goals:

- Establish project structure, tooling, and schemas.

Deliverables:

- TypeScript monorepo scaffold.
- Shared review story and comment schemas.
- CLI entrypoint.
- Basic test setup.
- `.rearview/` metadata conventions.
- Prepping-for-review skill.

### Phase 1: Local diff story MVP

Goals:

- Make local review useful without AI.

Deliverables:

- Load a local repository and choose review target: working tree, staged, branch vs base, or commit range.
- Parse git diff into files and hunks.
- Deterministic story builder using commit trailers, commit order, file categories, and path heuristics.
- Web UI for story outline, section descriptions, file list, and expandable diffs.
- Mark section/file as reviewed.
- Persist story state to `.rearview/review.json`.
- Export Markdown summary.

Suggested implementation order:

1. Core schemas and fixtures.
2. Git diff parser.
3. Story builder heuristics.
4. Local server API.
5. Minimal web UI.
6. Persistence and export.

### Phase 2: Structured comments

Goals:

- Add the review conversation layer.

Deliverables:

- Add line, hunk, file, section, and review-level comments.
- Comment intent dropdown and severity controls.
- Markdown renderer with embedded Rearview metadata comments.
- Thread display and resolution state.
- Export comments in a platform-friendly format.
- Import previously exported local comments.

### Phase 3: AI story and risk guidance

Goals:

- Use AI to improve review order and attention management.

Deliverables:

- AI provider abstraction with initial adapters/configuration for at least Codex and Claude.
- Environment-variable configuration for AI credentials, including Codex/OpenAI and Claude/Anthropic tokens.
- Prompt and structured output schema for story generation.
- Context preview before sending code.
- AI-generated section summaries, reviewer focus, and risk badges.
- Regenerate story while preserving user edits where possible.
- AI risk notes shown as draft guidance, not authoritative facts.

### Phase 4: GitHub integration

Goals:

- Review real pull requests while syncing comments.

Deliverables:

- GitHub token auth through environment variables for the local app, documented before any OAuth-based flow.
- Import PR metadata, diff, commits, comments, checks, and review status.
- Post line comments and review summaries.
- Render structured comment metadata into Markdown.
- Read and reply to existing threads.
- Map Rearview line positions to GitHub diff positions.

### Phase 5: Self-review story authoring

Goals:

- Let authors shape how reviewers consume a PR.

Deliverables:

- Drag-and-drop sections and files.
- Edit section titles, summaries, and reviewer guidance.
- Add author notes and callouts.
- Generate PR/MR body section from the story.
- Detect commit trailers and seed sections.
- Generate a commit rewrite plan with commands and safety checks.

### Phase 6: AI reviewer agents

Goals:

- Add configurable review personas.

Deliverables:

- Maintainer, Time traveler, and On-call engineer presets.
- Agent configuration UI.
- Run agents on selected sections/files.
- Draft comments with severity and confidence.
- Human approval before posting externally.
- Agent summary per section and whole review.
- Comment budget and duplicate detection.

### Phase 7: GitLab integration

Goals:

- Reach parity for GitLab merge requests.

Deliverables:

- GitLab token auth through environment variables for the local app, documented before any OAuth-based flow.
- Import MR metadata, diffs, commits, discussions, and pipelines.
- Post discussions and replies.
- Submit review-like summaries using GitLab-supported primitives.
- Provider capability matrix tests.

### Phase 8: Future surfaces feasibility

Goals:

- Keep the local app stable while evaluating whether a Chrome extension or hosted app is worth adding later. Prefer extension feasibility first unless product needs clearly require hosting.

Deliverables:

- Chrome extension feasibility spike.
- Hosted app feasibility spike, without choosing a cloud platform yet.
- Runtime boundary review for what can run in the browser, extension, local server, or possible hosted service.
- Authentication design options beyond environment variables, such as OS keychain storage, OAuth, browser extension auth, or hosted secret storage.
- Privacy review for any future surface that might handle repository contents or AI context outside the local machine.

### Phase 9: Advanced review intelligence

Goals:

- Deepen the story model and context discovery.

Deliverables:

- Symbol extraction and code outline by language.
- Call graph and test relationship hints.
- Generated-file and mechanical-change detection.
- New-commit invalidation of reviewed sections.
- Review fatigue metrics and pacing recommendations.
- Search across story, comments, code, and provider metadata.

### Phase 10: Ecosystem

Goals:

- Prepare for broader workflows after the local app and any future surface decisions are validated.

Deliverables:

- Browser-side provider view overlays if a Chrome extension is pursued.
- Public plugin/provider interfaces.
- Custom reviewer-agent marketplace or local config.
- Export/import bundle format for archival review stories.

## 12. Open questions

1. Which AI authoring tools beyond Codex and Claude should receive first-class session adapters first?
2. Should `.rearview/review.json` usually be committed, ignored, or split into committed story metadata and ignored private state?
3. If a hosted app is ever added, should it cache repository contents at all, and what explicit user controls would be required?
4. Should review story edits sync into PR/MR bodies automatically or only by explicit action?
5. What is the minimum acceptable GitHub/GitLab comment-position fidelity for the first provider integrations?
6. How should Rearview represent comments that apply to unchanged context lines?
7. Should agent reviewers be allowed to mark comments as blocking, or only suggest blocking severity for a human to approve?
8. How should commit rewriting be exposed safely for branches that are already shared?
